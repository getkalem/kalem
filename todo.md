# Kalem — Work Breakdown

Derived from `design_document.md`. Every item references the relevant section with `§`. When the design changes, update the document first, then this list.

Markers: `[ ]` to do · `[x]` done · `[-]` cancelled · `[~]` in progress
IDs: `T<phase>.<group>.<n>`; decisions are `D<n>` (§21).

How this list is used (owner, 2026-09-30): planning writes the tasks here, each with its reason, its test and its done-criterion, and never implements; implementation works the list in order, marks progress (`[~]`, `[x]`) and adds the "done:" notes, and never re-decides a `[-]`. A task that turns out wrong is questioned here, not worked around in code.

Phases are sequential. The next phase does not start before the current phase's **exit criteria** are met.

### 2.13 The Kalem format (RFC 0003; design_doc2.md §3 to §9 and §11; owner, 2026-09-30)

The format of `rfcs/0003-kalem-format.md`: one command syntax `\name[attributes]{content}`, paragraphs by blank lines, `$…$` as the only shortcut, LaTeX mathematics unchanged, Org's structure, Word's styles, fields and review marks, layout in `.klms` stylesheets, canonical serialization, the editor's well-formedness guarantee, Typst and LaTeX as PDF engines. Track B of design_doc2.md §11: it runs beside the standard modes and never ahead of them. RFC 0003 draft 0.2 is the working specification (accepted by the owner, 2026-09-30); its open questions close inside the tasks below.

**Now: only pure Org in `.org` (owner, 2026-09-30)**

The owner found font family and font size in an Org file. Org has no such thing; they are Kalem's additions of 2.2a, written as `@@kalem:…@@` snippets, `#+ATTR_KALEM:` lines and a `#+KALEM:` keyword behind the `org.allow_kalem_markup` opt-in. The rule for every format is the same, now principle 8 of the design document (§4.1): implement the original specification and add nothing; only `.klm` is Kalem's own. The additions belong to the Kalem format, where they return as styles and spans (T2.13.5, T2.13.8). Until then they are not offered anywhere.

### 3.7 Every file opens: viewer and editor plugins for PDF, Office files and images (`getkalem/plugins`; asked by the owner, 2026-09-30)

The aim: a click on any file in the file manager opens it, so Kalem is one application that views and edits everything, with `.klm` as its own format. Text files open in their modes (2.6). Every other kind opens through a plugin installed from `getkalem/plugins`: PDF, Word (`.docx`), Excel (`.xlsx`), PowerPoint (`.pptx`), images and SQLite databases are plugins, never part of the core (D29, D54). The core carries only the contract they implement, the two frontends' views of it and the fallback when none is installed.

**Opened as itself (owner, 2026-09-30; D55; principle 8, §4.1).** Kalem respects every format and never converts a file to another format in order to open or edit it. A Word file opens as a Word file and is edited as WordprocessingML says, an Excel file as SpreadsheetML, a PDF as PDF; no dialog ever asks to convert it to `.klm` or to anything else, unlike LibreOffice's prompts. The three rules of the standard modes (the Book, Part II overview) hold for these formats too, applied to their packages: **parts, never the package** (an edit rewrites only the XML part or the PDF object it touches; every other entry of the archive is copied byte for byte, compression included, so a file opened and saved without edits is identical), **no extension** (Kalem writes nothing the format's specification does not define, and nothing of its own), **unknown constructs stay visible** (what a plugin does not render is shown as a placeholder naming what it is, never dropped, and survives the save untouched). Conversion exists only as an explicit export command the user chooses, as for every format. Editing is offered only where the write-back is faithful; where it is not yet, the plugin is a viewer and says so.

**Specifications and oracles.** ECMA-376 (ISO/IEC 29500) for the Office formats, ISO 32000-2 for PDF, the image formats' own standards. Each plugin's chapter in Part IV of the Book follows the skeleton of T2.10.8 (D53), with the oracle named: Word, Excel and PowerPoint themselves for the hand checks of the exit criteria, LibreOffice headless (`soffice --convert-to`) in CI, pdfium or MuPDF renders for PDF, the reference decoders for images.

**Rules of construction.** Pure-Rust decoders compiled to WebAssembly components and sandboxed (D28); no C libraries (pdfium, MuPDF, Poppler, libxml2) in a community plugin, they belong to the compile-your-own tier only, with one exception: a format's own reference implementation, public domain or permissively licensed, compiled from source into the component by the registry's CI, because it is the only correct way to write that format (SQLite, D60). A plugin never draws: it returns a view model that both frontends render (a page bitmap, a block tree, a grid, a slide's display list), so the terminal shows pages and slides as images where it can (kitty, iTerm2, sixel) and as extracted text elsewhere (principle 7). A plugin reads through a host file handle, lazily, so a 200 MB PDF is not copied into WebAssembly memory. Order: the contract, then the image viewer (smallest; proves the contract and the terminal path), PDF, Excel, Word, PowerPoint. Depends on the host and the API source of 3.1 (T3.1.1 to T3.1.3, T3.1.17).

### 3.8 Language plugins with their language servers: Python, Elixir, the web languages, PHP, Go, Rust, C and C++ (`getkalem/plugins`; asked by the owner, 2026-09-30)

A language plugin makes Kalem a complete editor for a programming language without making it an IDE (§1.4 amended): highlighting, the language pack hooks (outline, format, completion, diagnostics; T2.7a.7), and the whole of what the language's server offers, working as well as it does in the editors people compare Kalem with: completion with snippets and automatic imports, hover, signature help, diagnostics, definition, references, implementation, type definition, rename across files, code actions and quick fixes, formatting, document and workspace symbols, semantic tokens, inlay hints, folding, document highlights and code lenses. The owner asks for Python and Elixir first, with the server integration complete and correct, then HTML, CSS and JavaScript, PHP, Go, Rust, and C and C++ (2026-09-30). Each language is one plugin (C and C++ share one, as they share their server and their headers), built in that order on the same manifest, so the later ones are mostly declarations and a corpus.

**Where the pieces live (D57, decided by the owner, 2026-09-30).** One language server client, and only one, is infrastructure in the core, `kalem-lsp`, like the plugin runtime itself: it speaks the protocol to whatever server a plugin declares and runs one server process per language per project root, so nothing per language ever enters the core. It is protocol plumbing every language shares, whose correctness (position encoding, incremental synchronization, workspace edits through the transaction stack, cancellation) touches the text engine at a granularity a plugin cannot reach, implemented and tested once. A language plugin carries the knowledge and no protocol code: file types, the highlighter, the server or servers and how to find or install them, project detection, formatter, run and test commands, settings and snippets, declared in its manifest, plus optional Rust code for language-specific extras (virtual environments, Mix). The core knows no language. This replaces the "LSP bridge as a user-installed plugin" of §11.12 and T3.3.2.

- **Why.** Python is the language of Kalem's scientific audience and of Babel's most used blocks; Elixir is the owner's; the web languages are what every export of Kalem produces and what most people edit beside a document; and one complete client makes the fourth language a manifest, not a project.
- **How it is tested.** A fake server in `tests/lsp/` scripted per feature (capabilities, responses, delays, crashes); the two real servers in CI on a corpus project each, with completion, hover, diagnostics, definition, rename, format and code actions asserted at known positions; latency measured (the editor never waits on the server; a completion list shows within 100 ms of the server's answer); the terminal covered by the same tests.
- **Done when.** A Python and an Elixir project open with every feature of T3.8.2 working in both frontends, the servers found or installed with consent, crashes recovered, and both plugins in `index.json` with their chapters.
