Kalem can be changed in two ways. The first is data: settings, key
bindings and themes, in files that Kalem reads, checks and reports on;
that way is available today. The second is code: plugins, which add
modes, completers, block types, link types, views and export formats;
that way is designed and decided (D25, D28, D29), and its runtime runs
viewers and extension plugins today. Every planned item below is named
by its task in =docs/todo.md=.

"Available" means it works in the current version, in both editors,
and this Book describes it from the code. "Planned" means the design
is decided and the task is open; the names and shapes given for it
may still change.

* The principle: new features, same format

Plugins must be able to add real features, new block types, link
types, views, export targets and document checks, while every
document stays valid Org that Emacs opens without Kalem. So *plugins
extend semantics, not syntax*: the parser's grammar is fixed, and
plugins give meaning to the extension points Org already has, as
Emacs packages do: special blocks (=#+BEGIN_kanban=), source block
languages (=#+BEGIN_SRC mermaid=), link types (=[[jira:ABC-123]]=),
drawers and properties, keywords, tags and TODO keywords, export
snippets and macros, dynamic blocks. A document that uses a plugin
still opens in Emacs, and in Kalem without the plugin, as ordinary
Org.

* A small core, one contract

The core of Kalem is five things (D29): Org, with its parser, model,
editing, tables and export engine; the Markdown, CSV and LaTeX modes;
the text engine with the view model; the two frontends; and the
infrastructure that runs before any plugin: commands, keymaps,
settings, files, projects, search and the plugin loader. Everything
else is to be a plugin on the public contracts, the common ones
bundled inside the binary as WebAssembly components, and new modes
and file types are developed in =getkalem/plugins=, never in the
core. Today the core holds more than this: the export back-ends
beyond HTML are built in, because the runtime they would move to
does not exist yet.

Highlighters, document modes and completers each have one contract,
shared by the built-in ones and by plugins (D25), so a plugin can do
everything a built-in does and the contract is proven before any
plugin uses it. The completer contract and the document mode contract
exist in =kalem-core= today ([[file:completers-and-modes.org][Completers, modes and highlighters]]);
the plugin side of each is phase 3.

* What you can change today

- *Settings.* =settings.toml= in the settings directory, and
  =.kalem/settings.toml= in a project, which applies over yours. Every
  value is checked; a wrong one is reported and the layer below
  applies. Tables under =plugins.<id>= and the list =plugins.enabled=
  are accepted for plugins and wait for the loader. See [[file:../part-1/settings.org][Settings]].
- *Keys.* =keymap.json=: add, change and remove bindings, with
  arguments, when-clauses and terminal variants. See
  [[file:commands-and-keys.org][Commands, scopes and keys]].
- *Themes.* =themes/light.toml= and =themes/dark.toml= change any color
  of the built-in themes: the page, text, links, the selection, TODO
  keywords, headline levels, and six colors of source code
  (=keyword=, =string=, =comment=, =number=, =function=, =type=).
  Themes with other names are planned with the plugin API.
- *Document modes of files.* A mode line on the first line
  (~-*- mode: org -*-~), and /Set Document Mode/, remembered in the
  workspace's =files.modes=.
- *Scripts.* The =kalem= command line checks, formats, exports,
  queries and completes files without a window. See
  [[file:../part-1/the-command-line.org][The command line]].

Adding a command, a completer or a mode today means changing Kalem's
source: the contracts are Rust types in =kalem-core=, described in the
chapters that follow for contributors, and for the plugin authors who
will implement them later.

- [[file:commands-and-keys.org][Commands, scopes and keys]]: the command registry, scopes, the
  when-clause language and keymap files. Available.
- [[file:completers-and-modes.org][Completers, modes and highlighters]]: the completer and mode
  contracts as implemented, and highlighting. Mostly available.
- [[file:plugins.org][Plugins]]: the plugin model in short. Planned.
