*Everything in this chapter is planned*, except language plugins,
which are declarative and load today ([[file:language-plugins.org][Language plugins]]). The host
that runs components exists (below) but Kalem does not load plugins
through it yet: the API it will grant, the loader and the commands are
to come. The design is decided
(D25, D28, D29) and written out in section 11 of
[[https://github.com/getkalem/kalem/blob/main/docs/design_document.md][the design document]]: the manifest, the API, the events, the
extension points and an example plugin. The work is groups 3.1 to 3.3
of =docs/todo.md=; the WIT definition (T3.1.3) is the one that will
count, and names may still change. This chapter says what the model
is, so that plugin authors and contributors can see where Kalem is
going. What you can extend today is in [[file:overview.org][The extension model]].

* The model

- *A plugin is a WebAssembly component*, written in Rust against the
  =kalem-plugin= crate, which is generated from the API's definition in
  WIT. It sees only what the API grants: no file system, network, clock
  or threads of its own; its own memory, 64 MB by default; a time
  budget, 100 ms for a synchronous call. A plugin error never crashes
  Kalem, and a plugin that fails repeatedly is disabled.
- *One contract.* The trait a plugin implements is the one Kalem's own
  modes and completers implement, so one crate builds two ways: as a
  sandboxed component a user installs, or as a bundled plugin compiled
  into the binary. Kalem ships no runtime for other languages and no
  scripting engine.
- *Permissions* are declared in the manifest, approved when the plugin
  is installed and recorded in =plugins.toml=: =fs:read:workspace=,
  =fs:write:workspace=, =fs:read:all=, =net:fetch:DOMAIN=, and
  =subprocess= with a separate warning.
- *Out of process* for what cannot be a component: language servers
  and external tools talk JSON-RPC over standard input and output.
  From phase 4, a power user may compile plugins into their own Kalem
  binary, with native speed and no sandbox, by their own choice.

* The API

The API is defined in WIT, in =crates/kalem-plugin/wit/= (D6): the one
source both sides are generated from. A plugin builds against the
=kalem-plugin= crate (wit-bindgen); Kalem's host generates its side from
the same files (wasmtime). Today the definition holds one world:

- =document-viewer= (§11.13): a plugin opening files that are not text.
  It exports =describe=, =detect= and =open=, and a =document= resource
  with the viewers' contract (design §11.13): =structure=, =size=,
  =render= (a bitmap the host paints), =text=, =text-rects=, =text-at=,
  =info=, =search=, =links=, and the editor half (=edits=, =apply=,
  =modified=, =save=). It imports =files= only: the =file= resource of
  the one file the host opened for it, with its name, its size and the
  bytes the plugin asks for, never a path.

=crates/kalem-plugin/coverage.toml= lists every extension point of the
design (§11.10 to §11.13) with the WIT interface that defines it or the
open task that will; a test keeps it in step with the design document
and the task list. The grid of spreadsheets and databases, commands,
panels, modes, completers and the rest are planned there.

* The host

=kalem-script= runs components in wasmtime with its Cranelift compiler,
the engine chosen by measurement ([[file:../part-5/decisions/D28-plugin-abi.org][D28]]):

- A component is compiled the first time it loads and kept in the state
  directory, named by its hash and the engine's version and settings;
  later starts read it in a fraction of a millisecond. A file another
  engine wrote, or a damaged one, is compiled again.
- A plugin reaches only what Kalem grants it. Its imports are resolved
  against what the host defines for it and nothing else; one asking for
  more is refused, and the refusal names the import.
- Each call has a time budget, 100 ms by default, counted by a clock
  that ticks every 10 ms; a plugin past it is stopped. Each instance has
  a memory limit, 64 MB by default; a plugin asking for more gets an
  allocation failure, and Kalem tells the two apart from the plugin's
  own failures.
- A loaded plugin is shared by threads, each with an instance of its
  own, so parsers, renderers and completers run in parallel.
- Plugins are built for =wasm32-unknown-unknown= and wrapped as
  components, so they import nothing the API does not name; built for
  =wasm32-wasip2= a Rust component imports fifteen WASI interfaces it
  never uses.

A plugin is a folder with a manifest, =plugin.json= (its ID, the
component, the API version, activation events, permissions, and the
commands, key bindings and settings it contributes), installed under
=plugins/ID/= in the settings directory and loaded on its activation
events. Command IDs follow the registry's rule, dotted parts of
letters and digits each starting with a lower case letter, so an ID
has no hyphens. Plugin settings go in =settings.toml= under
=[plugins."ID"]=, and bindings for plugin commands in =keymap.json=
like any other.

* What a plugin can add

Commands and key bindings; link types; renderers for special blocks
and source languages; decorations; completers and hover text; input
rules; highlighters and document modes; views (a board, a timeline);
panels, as a JSON widget tree both editors draw; diagnostics with
fixes; export back-ends and filters; importers and paste handlers;
Babel executors; table functions; dynamic blocks; agenda views and
capture templates; command-line subcommands; themes. Each appears in
both editors and, where it makes sense, on the command line (=kalem
run=, =kalem check=, =kalem export --to NAME=). Plugins cannot change
the parser's grammar, draw outside the widget tree and SVG, or hold
the editor's thread beyond the budget.

A mode is the largest of these: =detect=, =parse= (a flat tree of
kinds and byte ranges, incremental), =grid= for table-like formats,
=edit= for Enter, Tab and toggles, the outline, formatting,
completion and diagnostics hooks, and an optional export. It returns
ranges, never text, so it cannot break the byte-exact round trip; it
has two levels, declarative (a syntax definition and a mapping to the
kinds, no code) and programmatic (a parser in Rust); and a
conformance suite every mode runs. The completer and mode contracts
as they exist today are in [[file:completers-and-modes.org][Completers, modes and highlighters]].

* Inspection and the repository

Kalem has no REPL. What remains of a live runtime is an inspection
panel (the loaded plugins with their permissions, budgets and errors,
the command registry, timings), hot reloading of a plugin whose file
changed, and a local debug socket, off by default (group 3.2).

Plugins beyond the core live in =getkalem/plugins=: one Cargo
workspace with a crate per plugin, a template that =kalem plugin new=
copies, and an index Kalem reads as a static file. Its skeleton exists
(T3.3.7). Components are never committed: CI builds every plugin
against the current WIT, and a tag builds, signs and publishes each
=.wasm=. =kalem plugin install=, =list= and =remove= work for
declarative plugins and components alike: a component released in the
index is downloaded, its SHA-256 checked against the index, and its
manifest read from its folder at the release's tag
(=pdf-viewer-v0.1.0=), which must name the same plugin and version; one
not released yet is built from its source and installed from its
folder. Two commands start and build a component:

- =kalem plugin new NAME= starts a plugin. Inside a checkout of
  =getkalem/plugins= it copies =template/= to =plugins/NAME= and renames
  it; anywhere else it writes a crate of its own in =NAME/= that builds
  alone.
- =kalem plugin build [DIR]= runs Cargo for =wasm32-unknown-unknown=
  (=rustup target add wasm32-unknown-unknown= once) and wraps the module
  as the component =main= names in =plugin.json=, with =wasm-tools=
  (=cargo install --locked wasm-tools= once; Kalem calls the tool rather
  than carrying its 2.3 MB). It prints what the component imports and
  exports: a plugin imports only what its WIT world names.

=kalem plugin verify= is planned.

* Viewers as components

A viewer written against the Rust contract of =kalem-viewer=, as the
bundled ones are, builds as a component with one line,
=kalem_plugin::export_viewer_of!(PdfViewer)= under
=#[cfg(target_arch = "wasm32")]=: =kalem-plugin='s adapter writes the
=document-viewer= world over the trait, and the plugin reads the file
the host gives it through the same =FileHandle= API, piece by piece.
The PDF and image viewers of =getkalem/plugins= build this way.

=kalem plugin install DIR= installs a viewer whose component is built
(=kalem plugin build DIR=); it says which files it opens before asking.
At start Kalem registers the installed component viewers in place of a
bundled viewer of the same name (=org.kalem.pdf-viewer= replaces
=pdf-viewer=), and a thread compiles them, or reads them from the cache
in the state directory, so the first file they open does not wait.
Each document a component opens gets an instance of its own; one that
traps or runs past its time answers no more, and its document keeps
what it last said (its units, and whether it has unsaved edits, so
closing still asks) while the failure goes to the log. A
viewer's limits are 1 GB and 10 s a call, more than §11.6's defaults,
since a viewer holds a whole file; a manifest may set others,
=limits.memory_mb= and =limits.time_ms=.

* Versions of the plugin API

The plugin API is the WIT package =kalem:plugin= (=crates/kalem-plugin/wit=),
version 0.2.0; a component's manifest names the version it was built
against (="api": "^0.2"=). The rules, so that a plugin built once keeps
working:

- A released interface never changes: no function, field, case or type
  of it is added, removed or altered. The released ones (=viewer=,
  =files=, =clock=, =grid=) are copied in =wit-frozen/0.2.0/=, and a test
  (=tests/frozen.rs=) fails a change to them.
- What is new goes into a new interface (=grid-2=, in a file of its
  own) released with the next patch version (0.2.1); the worlds, kept in
  =worlds.wit=, export it. Kalem binds the interfaces a component has, so
  one built against 0.2.0 still runs on a Kalem of 0.2.1, without what
  it does not export.
- Something removed stays as a function that refuses, until a new minor
  version (0.3) is cut for everything at once.

Components from before 0.2.0 (the manifests that say =^0.1=, built while
the API had no version and changed with every spreadsheet feature) are
not tried: Kalem says the plugin needs an update and opens their files
with the bundled viewer. A component that cannot be bound for another
reason is treated the same way (in the status bar, and on =kalem view='s
standard error).
=kalem plugin check= starts every installed component viewer once, as
opening a file would, and exits 1 when one cannot run; the /Released
plugins/ workflow runs it on the index's plugins every day and when the
WIT files change, so a contract change shows which plugins need a new
release.

A viewer of sheets of cells, a workbook's or a database's, builds
the same way with =kalem-plugin='s feature =grid=: its component
exports the =grid= interface beside =viewer= (the =spreadsheet-viewer=
world), the grid half of the contract typed in WIT (cells and their
styles, edits, conditional formats, validations, sorting and filters,
charts, pivot tables, undo, macros), and Kalem uses it as it uses the
bundled one. A macro's questions cross as answers given so far: the
plugin stops at a question it has no answer to, Kalem asks the user and
runs it again with the answer. Every function of the contract is
carried to components; a test fails when one is added and not carried.

Viewers get one more interface, =clock=: the time, the user's time zone
and random bits. A workbook's =NOW()=, =TODAY()= and =RAND()= need them
to compute as Excel does, and they tell the plugin nothing of the user's
files; no other plugin has a clock. The Excel plugin's formula engine,
IronCalc, comes from =getkalem/ironcalc=, a fork whose only change lets
it read that clock on WebAssembly instead of a browser's JavaScript;
built so, the plugin opens, edits, recalculates and saves workbooks
exactly as the bundled one does, which a test checks workbook by
workbook (=KALEM_XLSX_COMPONENT=, =crates/kalem-cli/tests/xlsx_component.rs=).

Built for speed (=opt-level = 3=) and with WebAssembly's SIMD, which
=kalem plugin build= adds, the PDF viewer renders a page within a fifth
of its bundled speed: 39 ms against 33 ms for a page at a Retina
display's size. Built for size it was twelve times slower and no
smaller.

* Commands, keys and events

The =extension= world is a plugin that adds to the editor rather than
opening files. It imports the =kalem= interface, §11.4's namespace, and
exports =plugin=: =activate=, =deactivate=, =run-command= and
=on-event=. In Rust a plugin implements =kalem_plugin::kalem::Plugin=
and registers its commands with the functions that run them:

#+begin_src rust
use kalem_plugin::kalem::{self, EventKind, Plugin, Reply, Scope};

struct WordCount;
impl Plugin for WordCount {
    fn activate() -> Result<(), String> {
        let mut spec = kalem::spec("wordcount.show", "Word Count", Scope::only(&["org"]));
        spec.keys = vec!["ctrl+alt+w".into()];
        kalem::command(spec, |_args| Ok("null".into()))?;
        kalem::keymap("space n w", "wordcount.show", None)?;
        kalem::on(EventKind::DocumentBeforeSave, |_event| Reply::Proceed)?;
        Ok(())
    }
}
kalem_plugin::export_plugin!(WordCount);
#+end_src

A command's scope is part of its description, so none is registered
without one; the host refuses a scope naming no type, and an ID that is
not the plugin's own (=wordcount.=). Arguments and results cross as
JSON. =kalem::run= runs another command, built in or another plugin's,
once the plugin's call returns: right after the plugin's command, in
its context (a document's edit included), or at the editor's next tick
when an event's handler asked; it is refused at once when there is no
such command, and its result does not come back. A plugin calls its own
commands as functions, since a component is not entered again while it
is inside a call. A handle a registration returns may
be disposed of; dropped, it keeps the registration, and the host takes
back everything a plugin registered when it is deactivated. A vetoable
event's first veto is the answer. Each call has the plugin's time
budget; a command that loops is stopped.

Kalem loads the extension plugins installed: a component that opens
no files. =kalem plugin install DIR= installs one whose component is
built, and at start a thread loads each (compiled once and cached, as
a viewer is) and activates it when its manifest's =activation= says:
=onStartup=, the default, or =onEvent:NAME= at the first event of that
name (=onEvent:document:open=). A plugin is known by its ID's last part,
=org.kalem.wordcount= as =wordcount=, and its commands are
=wordcount.*=. Its commands join the palette, the menus' rules and the
keymap in both editors as it registers them, its key bindings come
before the profile's and the user's, its subscriptions hear the
editors' events, and its notifications show in the status line. A
plugin that traps or runs past its budget is stopped, what it
registered is taken back, and the user is told.

* The document

A plugin's command reads and edits the document it runs in through
=kalem_plugin::editor=: its text and selection, its headlines (level,
title, TODO keyword, priority, tags, properties, planning, parent and
children), the headline at a place or with an =ID=, those with a tag,
a keyword or a property, a headline's body, the TODO keywords and the
=#+KEY:= lines, the element at a place, and its tables with their rows
and formulas.

#+begin_src rust
use kalem_plugin::editor::{self, Query};

for h in editor::find(&Query { tag: Some("work".into()), todo: None, property: None }) {
    editor::set_todo(h.start, Some("DONE"))?;
}
editor::transact("Close the work items");
#+end_src

A headline or a table is named by where it starts. The plugin reads the
document as its command found it; its edits (insert, replace, the TODO
keyword through Org's own change with its logging, the title, tags and
properties, promoting, demoting and moving a subtree, a table's field
and its recalculation, an =ID= made on demand, saving) wait until the
command returns, then apply in order, each place moved by the edits
before it, and one undo takes them all back. An edit naming a place
where no headline or table starts is refused at once. Only a plugin's
own command reaches the document: its event handlers and panels do not.

* Settings, files and the network

A plugin reads Kalem's settings (=kalem_plugin::settings::get("editor.font_size")=)
and keeps its own in the user's =settings.toml=, under its ID:

#+begin_src toml
[plugins."org.kalem.wordcount"]
goal = 1000
#+end_src

=settings::own= reads them, =settings::set= writes them (the editors
read the settings again), and =settings::watch= hears a change, whether
the user edited the file or the plugin set it.

Files and the network are not a plugin's unless its manifest asks for
them, with the permissions of §11.6:

| Permission | Reaches |
|-
| =fs:read:workspace= | reading files in the projects' folders |
| =fs:write:workspace= | reading and writing there |
| =fs:read:all= | reading any file |
| =net:fetch:DOMAIN= | HTTP to that domain and its subdomains; =*= for any |

Without one, the plugin is not given the =fs= or =net= interface at
all, and a component that imports it is refused, the interface named
(D28). Paths are absolute, =..= is refused, and links are followed
before the check, so one cannot lead out of a project. A fetch does not
make the editor wait: =net::fetch= returns at once, and the response
reaches a closure later, fetched on a thread of its own.

* What a plugin shows

The same world imports =ui=, §11.4's =kalem.ui=: =notify=, the three
questions =prompt=, =confirm= and =quick-pick=, status bar items, and
panels. A question never makes the editor wait: the call returns at
once, and the answer comes later, a closure in Rust:

#+begin_src rust
use kalem_plugin::ui::{self, Level};

ui::confirm("Archive the done tasks?", |yes| {
    if yes {
        ui::notify("Archived", Level::Info);
    }
});
#+end_src

A panel is a tree of widgets (texts, buttons, inputs, checkboxes, list
and tree entries, progress bars, rows and columns) that the window and
the terminal each draw with their own; there is no webview (D11). A
plugin builds the tree with =ui::Tree=, adding each widget under one
already there, and replaces the panel's content with =ui::set_panel=;
what the user does to a widget reaches the panel's handler with the
widget's key. The host checks every tree before an editor sees it.
Both editors show them with their own means. A question is one of the
editors' own: a line is asked for in the palette (the terminal's
minibuffer), a yes or no and a choice from a list are offered as a list
in the palette, and the answer reaches the plugin through the command
=plugin.answer=. A status item stands in the status line, a click
running its command in the window. A panel opens with View > Plugin
Panel (=view.pluginPanel=, offered while a plugin has one), beside the
text or under it; in the window a click on a button, an entry, a
checkbox or an input reaches the plugin, and in both editors Panel
Actions (=view.panelActions=) lists the widgets one acts on, so a panel
is used from the keyboard too; an input's new text is asked for in the
palette. Cancelling a question tells the plugin nothing yet, a list
offers one choice even when the plugin allows several, and a password
is not hidden as it is typed.
