A file type gets three things from Kalem beyond plain editing: a
/completer/, which offers completions at the cursor; a /highlighter/,
which colors its code; and a /document mode/, which renders it (Org as
a styled document, CSV as a grid, LaTeX with formulas typeset). The
design gives each one contract shared by the built-in ones and by
plugins (D25). This chapter says where each contract stands today.

| Contract       | State today                                                                                                                    | Code                           | Plugin side       |
|----------------+--------------------------------------------------------------------------------------------------------------------------------+--------------------------------+-------------------|
| Completers     | Implemented; three built-in completers use it                                                                                  | =kalem-core/src/completers.rs= | T3.1.9c           |
| Highlighters   | syntect with the built-in syntax definitions, and language plugins' (no code)                                                 | =kalem-highlight/src/lib.rs=   | T3.1.9g           |
| Document modes | The contract with its conformance check; CSV and the Kalem format on it, the editors still drawing each mode with its own code | =kalem-core/src/modes.rs=      | T2.7c.10, T3.1.9g |
| Language packs | Implemented and wired; no pack built in                                                                                        | =kalem-core/src/packs.rs=      | T3.1.9c, T3.1.9e  |

* Completers

A completer is a source of completions: Org's keywords and link
targets, LaTeX's commands and citation keys, the words of the
document. One contract serves all of them (design §11.12): the core
runs the completers that apply at the cursor, merges and ranks their
items, and shows one menu, the same in both editors. The contract is
a Rust trait in =kalem_core::completers=, implemented only inside
Kalem today; plugins will implement the same trait through the
generated bindings (T3.1.9c).

The menu opens by itself when a completer's trigger fires as you
type, and Ctrl+Space or Alt+/ (=edit.complete=) asks for it anywhere.
Down and Up choose an item, Escape closes the menu, Tab takes the
chosen item and so does Enter, except for a word from the document,
where Enter closes the menu and starts a new line. Taking an item is
one undo step. =kalem complete FILE:LINE:COL= prints the items at a
place, best first, one a line, as label, kind and completer separated
by tabs; it completes as if asked with Ctrl+Space and waits up to two
seconds for slow completers.

#+begin_src text
$ kalem complete notes.org:4:5      # line 4 is "#+ti"
#+title:	keyword	org
#+end_src

| ID      | Applies in                      | Trigger                                     | Priority | Items                                                                   |
|---------+---------------------------------+---------------------------------------------+----------+-------------------------------------------------------------------------|
| =org=   | Org documents                   | =#+=, =[[=, =[fn:= or =:= before the cursor |       10 | =#+= keywords and blocks, link targets, footnote labels, tags           |
| =latex= | LaTeX files                     | =\=, ={=, =,= or =[= before the cursor      |       10 | Commands, environments, citation keys, labels, files, packages, options |
| =words= | Every mode but the file manager | A word of three letters                     |        0 | Words of the document, nearest to the cursor first                      |

The words completer takes words of at least three letters that start
with the word being typed, ignoring case, from the megabyte of text
around the cursor, nearest first, at most fifty; in Org documents it
stays quiet where Org's own completion applies. A dictionary with
spell checking, a language server bridge and a model are not
implemented.

** The contract

#+begin_src rust
pub trait Completer: Send + Sync {
    fn id(&self) -> &'static str;                 // "org", "words"
    fn priority(&self) -> i32 { 0 }               // higher first among equals
    fn scope(&self) -> Scope { Scope::all() }     // the text types it serves
    fn applies(&self, ctx: &Context) -> bool;     // where else it applies
    fn trigger(&self) -> Trigger;                 // what opens its menu
    fn slow(&self) -> bool { false }              // run on another thread
    fn budget(&self) -> Duration { DEFAULT_BUDGET } // a slow one's time: 100 ms
    fn complete(&self, ctx: &Context, doc: Option<&DocumentState>,
                cancel: &Cancel) -> Vec<Item>;
    fn resolve(&self, _item: &Item) -> Option<String> { None }
    fn hover(&self, _ctx: &Context, _doc: Option<&DocumentState>) -> Option<String> { None }
}
#+end_src

=scope= gives the text types the completer serves, as a command's
scope does, by the type at the cursor, so a completer for =python=
also runs in a Python source block; =applies= decides the rest from
the context. A fast completer gets the document (=doc= is =Some=) and
runs on the editor's thread, so it must return quickly; a completer
whose =slow= is =true= runs on another thread with the context only,
and long work checks =cancel.cancelled()=. =resolve= gives
documentation for an item when it is chosen; =hover= gives text about
the thing under the cursor (no editor shows a hover card yet).

| Trigger           | Fires when                                                              |
|-------------------+-------------------------------------------------------------------------|
| =Strings(&[...])= | One of the strings occurs in the line before the cursor, or on request  |
| =WordPrefix(n)=   | The word before the cursor has at least =n= characters; on request, one |
| =Request=         | Only on request (Ctrl+Space, Alt+/)                                     |

The =Context= holds =text= (the document's text up to a megabyte,
else the megabyte around the cursor, starting at =base=), =point=,
=mode=, =text_type=, =path= and =requested=; its methods
=slice(range)=, =line_before()=, =paragraph_before()= and
=word_prefix()= give the text around the cursor. An =Item= has
=label=, =insert=, =range= (what it replaces, ending at the cursor),
=cursor= (where the cursor goes in =insert=), =kind= (=word=,
=keyword=, =link=, =tag=, =footnote=, =symbol=, =snippet=), =detail=
and =source=; =Item::new(label, insert, range, kind)= makes one.

At each keystroke that may complete, the =Registry= keeps the
completers that apply and whose trigger fires, runs the fast ones at
once and the slow ones on their own threads, adding their items as
they arrive; the next keystroke drops the old completion and sets its
cancel flag. Items with the same insertion over the same range count
once, and the list is ordered by items whose label starts with the
word being typed, then items accepted recently, then the completer's
priority. A slow completer that misses its budget (=budget=, 100 ms)
shows nothing for that keystroke and the menu keeps the others'
items.

** Writing a completer today

Inside Kalem, a new completer is a type that implements =Completer=,
added to =Registry::with_builtins= in =completers.rs= (the LaTeX
completer in =latex_complete.rs= is a complete example). A sketch that
completes a fixed list of words in Markdown after two letters:

#+begin_src rust
use kalem_core::command::Scope;
use kalem_core::completers::{Cancel, Completer, Context, Item, Kind, Trigger};
use kalem_core::DocumentState;

struct Glossary;

impl Completer for Glossary {
    fn id(&self) -> &'static str { "glossary" }
    fn scope(&self) -> Scope { Scope::only(&["markdown"]) }
    fn applies(&self, _ctx: &Context) -> bool { true }
    fn trigger(&self) -> Trigger { Trigger::WordPrefix(2) }
    fn complete(&self, ctx: &Context, _doc: Option<&DocumentState>, _c: &Cancel) -> Vec<Item> {
        let (start, prefix) = ctx.word_prefix();
        ["adjunction", "category", "functor", "morphism"]
            .iter()
            .filter(|w| w.starts_with(prefix))
            .map(|w| {
                let mut item = Item::new(*w, *w, start..ctx.point, Kind::Word);
                item.detail = "glossary".into();
                item
            })
            .collect()
    }
}
#+end_src

As a plugin, the same completer will be registered with
=kalem::completers::register= (T3.1.9c).

* Document modes

The modes today are a fixed set in the core (=DocumentMode= in
=mode.rs=):

| Mode         | Name in settings and =editorMode= | Files                                                          |
|--------------+-----------------------------------+----------------------------------------------------------------|
| Org          | =org=                             | =.org=, =.org_archive=, =.klm=                                 |
| Markdown     | =markdown=                        | =.md=, =.markdown=, =.mdown=, =.mkd=, =.gfm=                   |
| CSV          | =csv=                             | =.csv=, =.tsv=, =.tab=                                         |
| LaTeX        | =latex=                           | =.tex=, =.latex=, =.ltx=                                       |
| BibTeX       | =text=, language =bib=            | =.bib=, shown as a grid of entries                             |
| Plain text   | =text=                            | Everything else that is text, with a language for highlighting |
| Binary       | =binary=                          | Not opened for editing                                         |
| File manager | =directory=                       | Folders                                                        |

A mode is chosen in this order: the mode chosen with /Set Document
Mode/ (=view.setMode=), which the workspace settings remember by path
in =files.modes=; a mode line on the first line (~-*- mode: org -*-~
or ~-*- org -*-~; a name that is not a mode opens plain text with
that language); the extension; a =#!= line (=#!/usr/bin/env python3=
opens plain text in =python=); plain text without a language. A file
whose start has a NUL byte, or bytes that are not UTF-8 with many
control characters, is binary.

One contract serves every mode, the one built-in modes use and
plugins will use (§11.11): the trait =ModeSpec= in =kalem_core::modes=,
with =id= and =detect= (extensions and a sniff function over the
first bytes), =parse(text, edit?, previous?)= (a flat tree of nodes,
each with a kind from a fixed vocabulary, a byte range and its
parent), =grid(text)= (rows and cells with ranges, for table-like
formats), =edit= (Enter, Tab and toggles, each returning edits with
ranges), the language pack hooks =outline=, =format= and
=diagnostics=, and an optional =to_html=. A mode returns ranges into
the text, never text, so it cannot break the byte-exact round trip;
=modes::check= is the conformance check every mode runs: every range
inside the text and inside its parent, two parses equal, an
incremental parse equal to a full one. CSV, the Kalem format, Markdown
and LaTeX are written against it (T2.7c.10). LaTeX maps its syntax tree
to the kinds: sectioning commands as headings, levels counted from the
document's highest (a book's chapters, an article's sections are level
1); =itemize=, =enumerate= and =description= as lists, each item from
its =\item= to the next with what it holds; tables with rows ended by
=\\= and cells split by =&=; code environments with their language
(=minted='s argument, =lstlisting='s =language==); displayed and inline
mathematics; =\emph=, =\textbf=, =\texttt=, =\verb=, =\href= and =\url=
with their targets, =\includegraphics= with its file, =\footnote=; any
other command or environment by its name. Its outline is the
headings' titles, its formatter =kalem fmt='s, its diagnostics =kalem
check='s, Enter and Tab those of the editor; every file of the arXiv
sample passes =modes::check=. Still to come: the editors drawing every
mode from its tree, and the plugin side, =kalem::modes::register=
(T3.1.9g).

* Highlighters

Code is highlighted by =kalem-highlight=, one engine for plain text
files and for Org source blocks (D16). It uses syntect, which reads
Sublime Text syntax definitions, with pure Rust regular expressions;
the definitions are syntect's default set with those of =bat= added
(the =two-face= crate), built into Kalem: about two hundred
languages, listed in /Plain text and code/. A language name is looked
up, ignoring case, first in a table of Org's source block names that
differ from syntect's (=sh=, =shell=, =bash= and =zsh= are shell,
=elisp= is Lisp, =js= JavaScript, =py= Python, =tex= LaTeX, =dot=
Graphviz), then as a syntax's name token, then as a file extension; a
name that finds nothing is not highlighted.

The highlighter gives each span a /kind/ from the syntax's scope, not
a color: comment, string, number, constant, keyword, operator,
function, type, variable, tag, macro, invalid. The editors color the
kinds with the theme, whose six code colors (=keyword=, =string=,
=comment=, =number=, =function=, =type=) you can change in
=themes/light.toml= and =themes/dark.toml=. In plain text files the
highlighter keeps its state at each line, so after an edit only the
changed lines, and those after them until the state is what it was,
are highlighted again. A [[file:language-plugins.org][language plugin]] adds Sublime syntax
definitions from its folder, with no code: they come before the
built-in ones for their extensions, and =extends= (which syntect does
not know, and which Sublime Text's own syntaxes use) is resolved by
Kalem. The set with the plugins' syntaxes takes most of a second to
build, so it is built once and kept in Kalem's state folder until a
plugin changes.

* Language packs

A format whose view is its source (JSON, YAML, TOML, XML, a diff, a
ledger journal, a gettext catalogue) gets no document mode but a
/language pack/: four hooks on top of its highlighter, the same four a
plugin gives (=kalem_core::packs=, T2.7a.7).

| Hook          | What the pack gives                             | Where Kalem uses it                                          |
|---------------+-------------------------------------------------+--------------------------------------------------------------|
| =outline=     | Headings with their level, title and start      | The outline sidebar of both editors                          |
| =format=      | The formatted text, or a refusal with its place | Format Document (=hasFormatter=), =kalem fmt=, =kalem check= |
| =diagnostics= | Problems with a range, a code and a message     | The status bar, =kalem check=                                |
| =completer=   | A completer on the contract above               | The completion menu                                          |

A pack serves text types, the highlighter's language names (=json=,
=diff=), and a document in plain text mode with one of them gets the
pack's hooks. The status bar shows the problem on the cursor's line
or how many there are; Format Document refuses a text the formatter
refuses and puts the cursor at the place; =kalem fmt= lists it as "not
formatted" and fails, and =kalem check= prints each problem as
=FILE:LINE:COL: error[CODE]: MESSAGE=. The packs themselves are to be
plugins in =getkalem/plugins= (D29), registered through the plugin
host that comes with the WebAssembly runtime; until then the contract
is in the core with its wiring and tests, and no pack is built in.
