#+TITLE: Kalem and Emacs

Kalem takes more from Emacs than from any other editor, and leaves out
the one thing that makes Emacs what it is. This page says which is
which and why, so that the first question an Emacs user asks has its
answer written down.

* The short answer

Kalem has Emacs's architecture: every action is a command, keymaps are
data, each kind of text has its mode, the same editor runs in a window
and in a terminal, and every operation runs in batch. It has Emacs's
best applications: Org, Dired, Projectile, and the agenda and Babel on
the way. It does not have Emacs's defining property: a live Lisp
runtime in which the user reprograms the editor while it runs. Kalem is
not a modern Emacs and does not call itself one. It is an editor for
people who want what Emacs does for text files and do not want to
program their editor.

* What that costs

An Emacs user will miss three things, and Kalem does not pretend
otherwise.

- *Trying a thing in a minute.* =M-:= and =eval= let you change the
  editor without leaving it. Kalem has nothing at that speed. What it
  has: =keymap.json= binds any command with arguments to any key;
  =kalem commands= and the palette show every command; keyboard
  macros are being added (T3.7b.8); an inspection panel that answers
  "what did this key run, and where did this setting come from" is
  planned (T3.2.1). Anything beyond that is a plugin: =kalem plugin
  new=, Rust, a build.
- *Advice and redefinition.* Changing how a built-in command behaves.
  A command in Kalem has settings and a scope; a plugin can register a
  command on the same key with a narrower scope and take it over; it
  cannot change a built-in command's body.
- *The buffer as the universal interface.* A shell, mail or chat inside
  the editor. Kalem does not try: it edits files, and its terminal
  editor lives inside your terminal rather than the other way round.

What the same user gains: a start in a fraction of a second, a
document that looks like a document with its formulas drawn, the same
editor over SSH with images where the terminal draws them, a grid for
tables and CSV, and a file that Emacs reads back with a diff only where
it was edited.

* Working beside Emacs

An Org file edited in Kalem returns to Emacs changed only where you
edited it: tables aligned as =org-table-align= aligns them, tags at the
column the file uses, blank lines and indentation as the file has them,
and no keyword Emacs does not know. Emacs is the reference: =kalem
diff-emacs= compares every construct of a file with =org-element=, the
editing commands and the exporters are compared the same way, and the
deliberate differences are listed in
[[file:../part-2/org-known-differences.org][Known differences from Emacs Org]], each one a test.

For hands that know Emacs: =docs/keymaps/emacs.json= has Org's keys to
copy from, the Vim profile has Doom's leader, and the Doom leader table
in [[file:../part-1/keys.org][Keys]] lists every Doom key with what it does in Kalem or why it does
not yet. The file manager's keys are Doom's Dired keys.

* Is Kalem a "modern Emacs"?

By architecture, yes; by essence, no. The phrase promises a
malleability Kalem chose not to offer, and it starts an argument about
what Emacs is instead of a conversation about files. Kalem says instead:
Emacs's ways, without Emacs. The commands, the modes, the keys and the
applications, for people who do not want to program their editor. For
those who do, Emacs remains the better tool, and Kalem keeps their
files byte for byte.
